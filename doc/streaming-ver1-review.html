结论

只有一个问题需要立即处理：tailUtf8 在多字节文本上退化为 O(n²)，实测单个事件可阻塞渲染主线程 14 秒。

P0 · tailUtf8 的二次退化

P0

每次循环都做一次完整 UTF-8 编码

apps/renderer/src/conversation/conversationStore.ts:45-50 · 调用点 :210 · 重放路径 :134

function tailUtf8(value: string, maxBytes: number): string {
  if (utf8ByteLength(value) <= maxBytes) return value;
  let low = Math.max(0, value.length - maxBytes); let result = value.slice(low);
  while (utf8ByteLength(result) > maxBytes && low < value.length) result = value.slice(++low);
  return result;
}

每次循环都是一次 String.slice 加一次完整的 TextEncoder.encode。low 的初值 length - maxBytes 只在纯 ASCII 下正确；CJK 每字符 3 字节，初值会差出三分之二的距离，于是逐字符收敛。

实测数据（把该函数原样抠出在 Node 中运行，非理论推导）：

输入迭代次数耗时
30,000 个中文字符8,155765 ms
60,000 个中文字符38,1559,120 ms
120,000 个中文字符43,69114,238 ms
200,000 个 ASCII 字符11 ms
P0

触发路径由两个缺陷叠加而成

  1. 投影器 #onToolUpdate（conversation-live-projector.ts:526）只在 sanitized.text.startsWith(previous) 成立时发 append。任何重绘型的部分结果 —— 进度条、重排的表格、带 spinner 的输出 —— 前缀检测都会失败，于是 updateMode 保持 "replace"，output 是整份累积文本，上限 TEXT_BLOCK_MAX_BYTES = 256KB。
  2. 256KB 中文约 87,000 字符，进入 conversationStore.ts:210 的 tailUtf8(candidate, 64KB)，约 43,691 次迭代 → 每个 update 事件冻结 14 秒。

更糟的是 hydrate() 在 :134 同步重放 replay 事件，所以打开一个尾轮带大段中文工具输出的会话就会直接卡住。

append 路径也不便宜，而且分两段。tailUtf8 没有 truncateUtf8 那样的长度快路径，所以任何一次调用都至少做一次完整的 utf8ByteLength 编码：候选文本仍在 64KiB 以内时，是每事件一次约 64KB 编码（60 事件 / 秒约 4 MB/s）。而一旦某个工具的输出越过 64KiB，tool.output 就永久停在上限附近，此后每一次 append 的 candidate 都会超限并进入循环 —— 迭代数约等于新增字符数，每次迭代再编码约 64KB。按 100 个 CJK 字 / 事件、60 事件 / 秒估算约 390 MB/s；这是估算值，实际取决于 delta 速率与字符宽度。

P0

修法

正确的原语已在同一文件第 8 行 import 进来。truncateUtf8（packages/studio-protocol/src/conversation-text.ts:22）的镜像写法是单趟的：编码一次，从 bytes.length - maxBytes 这个起点向文本末尾方向推进，直到落在码点起始字节上（(byte & 0b1100_0000) !== 0b1000_0000），再 decoder.decode(subarray)。约 5 行，复用现成的模块级 encoder / decoder，并返回 { text, truncated }。

方向不能照抄 truncateUtf8：它保留头部，所以从 maxBytes 处向前回退找边界；tailUtf8 保留尾部，起点是 bytes.length - maxBytes 且必须向后推进 —— 向前回退会让保留的字节数超过 maxBytes。

顺带去掉 :210 那句 output !== candidate：它是两个最多 256KB 字符串的全量比较，只为推导一个截断标记，而单趟实现自己就知道有没有截断。

虚拟化的定位问题

P1

scrollMargin 感知不到上方内容的高度变化

apps/renderer/src/conversation/ConversationVirtualList.tsx:50-56 · 兜底分支 :62-65

主要问题（恒成立）：ResizeObserver 观察的是 host 自身（:55），而 scrollMargin 取决于 host 上方兄弟节点的高度总和 —— StatusBanner、notices、xd:// 挂载通知、「加载更早」按钮。这些出现或改变高度时，host 的 offsetTop 变了但自身尺寸没变，update() 不触发。

次要问题（条件性）：:62-65 的「未测量」兜底分支返回的 div 没有绑定 ref={hostRef}，走这条分支时 effect 因 hostRef.current === null 提前返回，而依赖只有 [enabled]，之后不会重跑。由于 initialRect: { height: 800 }（:39）在首帧就能给出非空区间，这条分支只在测量到零高视口时才走（折叠面板、隐藏页签、入场动画）。

参照物的脆弱性（当前不是 bug）：offsetTop 相对 .convo-doc 计算，所以 .convo-scroll 的滚动原点到 .convo-doc border-box 顶部之间的一切它都看不见。当前恰好为 0（.convo-doc 是 margin: 0 auto，.convo-scroll 无 padding），一旦有人给滚动容器加 padding 或给 doc 加 margin-top 就会静默偏移。修的时候直接用两个 getBoundingClientRect().top 相减加 scrollTop 更稳。

后果是 translateY(item.start - scrollMargin)（:74）与虚拟化器的可视区间计算同时偏移，偏移量取决于上方布局变化的幅度：行可能画到 banner 区域，挂载的索引区间也可能与实际滚动位置不符。另外 scrollMargin 是 useState 又被读进 useVirtualizer 的 options（:40），在 layout effect 里 set 它等于挂载时必定多一次「渲染 + 全量区间重算 + 布局」。

capVirtualItems 截错了一端

apps/renderer/src/conversation/ConversationVirtualList.tsx:8-11

if (items.length <= max) return items;

getVirtualItems() 返回的是当前区间内按索引升序的项，slice(0, 120) 保留的是视口最上面那 120 行。对一个 pin 在底部的对话流，一旦区间超过 120，被丢掉的正是用户正在看的底部 —— 视口下半截空白。

minimap

P1

混用逻辑索引与实际像素两套坐标系

apps/renderer/src/conversation/ConversationMinimap.tsx:381-394

先用 index / (n-1) 给全部 mark 播种（行索引空间的均匀分布），再用 center / scrollHeight 覆盖已挂载的那十几行（真实像素空间）。两者只在所有行等高时一致。真实转录行高差十倍，于是已挂载圆点相对邻居跳位，滚动时圆点随挂载窗口进出而反复跳动。

更实质的后果：spaceMinimapMarks（:212-215）假定 entries 按 f 升序（它是向前单调游走的），而混合坐标系下 f 不单调，聚类判断因此出错，可能产出重叠的圆点。建议统一坐标来源 —— 虚拟化器的 item.start 已经持有全表位置信息，正是为此而生。

P1

每帧重新测量与全表扫描

apps/renderer/src/conversation/ConversationMinimap.tsx:367 · :381-393 · :217/:220

measure() 的跳过条件是「marks 未变 且 scrollHeight 未变」。虚拟化下 scrollHeight 随虚拟化器持续测量行高而一直在变，这个 gate 在流式期间基本不成立。于是每帧执行：分配一个最多 2000 键的 next 对象；querySelectorAll 后对每个挂载节点读一次 getBoundingClientRect()（强制同步布局）；setFractions 触发 spaceMinimapMarks 重算。

spaceMinimapMarks 里两个 findIndex（:217 / :220）每次都从索引 0 开始扫，谓词对 idx < i 只是返回 false 而不是跳过。在 2000 个 mark、约 55 个均匀簇（MIN_MARK_GAP = 0.018）的典型情形下，扫描量可达数万到十万级；最坏情况 O(n²)。改成 for (let k = i; k <= j; k++) 即降到 O(n)。

好消息：渲染出的圆点被 MIN_MARK_GAP 收敛过，DOM 节点数是有界的 —— 这一层没问题。成本全在测量与布局阶段。

jumpTo 兜底路径的分母不一致

#store 每次用 new TextEncoder().encode(JSON.stringify(event)) 计算事件字节数（编码器实例也是每次新建）。#rememberDelta 另做一次编码（:304），并在 :312 把 previousEvent.delta + addition 送进 truncateUtf8(..., DELTA_MAX_BYTES) —— 其 O(1) 快路径条件是 length * 3 <= maxBytes（约 10922 字符），累积 delta 一旦超过这个长度，每个 delta 都要对最多 32KB 做一次完整编码。按 16ms 合并约 60 次 / 秒 / 会话，乘以并发会话数，全在主进程 —— 会拖累所有 IPC。

准确的范围：正常且能记入 replay 的流式事件基本都会付这份成本，例外有三处 —— 块已达 TEXT_BLOCK_MAX_BYTES 后 addition 为空的提前返回（:305-308）、会话已 overflowed（:241 / :295）、replay 已淘汰且事件属同一被淘汰轮次（:157-160）。三者性质不同：第一条是预期内的限流行为（文本块达到上限本身正常），后两条才是 replay 的降级路径。

架构风险

P2

structureToken 是隐含不变量

apps/renderer/src/conversation/conversationStore.ts:337 · ConvoTranscript.tsx:149-156

纯文本 delta 时 rows 是新数组但 structureToken 不变，因此 binds / createdBinds / visualItems / itemKeys / latestAssistant 都不重算，算的是上一帧的 rows。这依赖一个隐含约定：token 不变时行数与行结构不得改变，只能改已有行的内容对象。

当前路径基本遵守（文本 delta 与工具输出更新不改行数；消息完成、工具开始、turn 完成等结构事件会换 token），所以这是架构风险而非已复现崩溃。但一旦出现「行数变化而 token 未变」的路径，itemKeys.length 与 visualItems.length 就会不一致，renderItem 里的下标访问直接崩。建议加开发期断言或专门测试。

P2

同步入队后立即 drain，队列长度恒为 0 或 1（我核过重入场景：外层 #drain shift 后队列已空，listener 重入 #emitParsed 时内层 drain 会清空，外层 while 随即退出）。因此 #enqueue 的 delta 合并（:1001-1030）、#compactQueue()（:1047-1081）、CONVERSATION_LIVE_QUEUE_LIMIT 丢弃策略（:1032-1043）在当前调用路径下都不会激活。实际只剩上游 16ms / 64 字符的定时合并在起作用。

未来若改成异步 listener 或新增调用路径，队列可能真正增长。所以准确的说法是「当前正常路径未激活这套背压设计」，而不是死代码 —— 但它会误导后来的人以为背压已经存在。
