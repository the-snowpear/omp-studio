## 已修复的问题

| 问题与影响 | 改动 | 证据 |
|---|---|---|
| 评测状态入口在一次慢查询期间，每个变更事件再启动查询，完成后各自创建轮询链 | 状态入口、详情和历史共用 `evaluationPolling.ts`；同一作用域只保留一个在途读取，期间的变更合并为一次补读 | 25 个并发变更事件：修复前未完成查询已达 26 次；修复后在途仅 1 次，完成后补读 1 次；后续 15 秒只增加 3 次五秒轮询 |
| 评测详情每个事件重启 effect，旧请求未完成又开始读取；隐藏窗口继续刷新 | 事件由读取调度器合并；隐藏时取消计时和后续读取，返回立即刷新；历史仍按事件刷新 | 详情与历史、隐藏一分钟、恢复、卸载后的行为测试通过；预览全流程不调用真实 API |
| 浏览器加载状态、文档 ID、导航按钮与 DevTools 状态触发整份 `browser.json` 重写 | 比较持久化字段后才排队写盘；所有状态更新仍通知界面 | 25 次临时更新：修复后文件修改时间不变，界面回调仍有 25 次；导航后重开存档恢复新标题和 URL |
| 浏览器状态读取会创建不存在的会话，后续连同整份存档保存 | `state`、`initialControl` 使用无副作用查询，释放未打开的会话也不创建记录 | 读取 1,000 个未打开网页的聊天，再创建一个真实标签：存档会话数从 1,001 变成 1 |

页面刷新只影响读模型。评测 Worker 的执行、审批、停止和保存仍由 Host 负责；浏览器保存格式、权限、控制权和标签恢复语义保持原样。

## 测量结果与边界

环境：Windows，Intel i9-13900HX，32 个逻辑处理器；脚本 Node 24.13.0；生产文件测试使用 Electron 43.4.0 / Chromium 150.0.7871.224，既有流式基线使用 Chromium 151.0.7922.34。不同引擎的数据不混为一次前后性能对照。

| 场景 | 结果 | 解释 |
|---|---|---|
| 流式基线，5 次采样 | 长／短历史单帧布局比 1.467；繁忙场景 p95 帧间隔 16.7ms；18 项检查通过 | 本日上一段对话在干净的同一基线提交测得；本轮未改该渲染管线，没有把它当作本轮提速结果 |
| 连续 token 批次 | 第 2／3 批强制 GC 后堆约 7.85／7.93 MB，比值 1.01；监听器均为 242 | 合成正文窗口的保留量稳定，不代表真实 Runtime 或所有内置网页的内存 |
| 完整工作台启动，5 次采样 | 启动到外壳中位数 1,093ms；首次 1,669ms；页面 reload 后 ready 中位数 217ms | 生产文件、独立 Electron profile、完整 App 合成夹具；未接真实 Host/Runtime，未清 OS 文件缓存；两个时间不是同一计时起点 |
| 真生产入口同步 JS | 3,027,283 bytes raw；953,507 bytes gzip | 从生产 `index.html` 递归统计静态 JS import；不含动态导入、CSS、字体、媒体。高于原目标 2.5 MB / 800 KB；gzip 仅用于体积对照，本地文件实际读取原始字节 |
| 高亮与 Mermaid，5 次采样 | 每次 100 块全部着色，无正文差异、重挂载或超预算高度跳变；压力队列及超大图限制通过 | 生产文件模式，独立验证输入响应与正文一致性 |
| 视图生命周期与空闲释放 | 50 次主／子视图生命周期后 Engine、Store 均回到 0；空闲 31 秒后高亮 Worker 为 0，所有 pending/slot listeners 为 0 | 100 项高亮缓存约 4.90 MB、Mermaid 缓存 1 项约 11.6 KB 仍在既有预算内，缓存保留不等于泄漏 |
| Windows 原生最小化／恢复 | 隐藏时发布计数没有增加；恢复后 10,000 字符完整可见 | 使用未连接 Playwright 的独立窗口验证，避免焦点模拟掩盖可见性 |

第一次资源释放测试在空闲等待阶段出现 `Target page, context or browser has been closed`，留下失败报告，原因未确定。保持代码、采样次数和阈值不变后复测通过；没有为通过测试修改门禁或产品逻辑。

## 后续优化优先级

| 优先级 | 代码依据与优化方向 | 验证方式／取舍 |
|---|---|---|
| P1：首屏同步加载 | `App.tsx` 仍同步引入 Git、Computer、ContextInspector 等工作台面板；生产入口本身约 2.16 MB，通用 vendor 约 677 KB。沿用 `DeferredPanel` / `LoadWhenVisible` 在首次实际打开时加载，再用模块体积报告定位 vendor 来源 | 保留面板状态与跨窗迁移，验证首次打开、错误重试和预览；与同机 5 次启动及首屏静态依赖体积对照。仅把一个文件改拆为几个静态 chunk 不会减少启动执行量 |
| P1：后台网页的 CPU／GPU | `managed-browser.ts` 的每个 `WebContentsView` 统一使用 `backgroundThrottling: false`。Electron 官方说明，一个窗口中的任一内容禁用它，可使整个窗口继续绘制换帧 | 区分可见、Agent 控制、人工闲置、下载／音视频后确定节流策略；先测多标签、最小化及托盘的进程 CPU/GPU。直接统一开启节流或自动卸载可能改变 Agent 操作、计时器与页面状态，需要产品决策 |
| P2：大型评测报告 | `evaluation-coordinator.ts` 的 `rows()` 每次调用 `#readRows()` 全量扫描 JSONL 后再分页；每次 revision 更新，`#saveRows()` 从 0 扫行，`#readChunks()` 重取完整 native report；启动时也会加载全部 record | 用大型合成评测量化主线程事件循环延迟、读取字节和序列化时间；优先采用按 revision 的索引或增量接口，保留更新同一 row key、重启恢复及历史准确性。不能用无界正文缓存换取少读磁盘 |
| P2：持续运行实测 | 现有 Main/Renderer/Runtime 数值采样和有界资源计数可复用，但本轮没有进行数小时真实会话与浏览器混合负载测试 | 设计 2–8 小时的空闲／流式／切换会话／网页／终端混合测量，分别看各进程 RSS、JS heap、external、Worker、监听器、事件循环延迟和唤醒次数；发现增长再用 heap snapshot 查保留链 |

现有高亮 Worker、Mermaid 队列／缓存、有界正文、后台发布、PTY ACK 流控和 Runtime 验签证据缓存已有专门实现。本轮不另建第二套调度或缓存，也不通过降低安全检查、删除历史或强制 GC 掩盖成本。

## 官方资料核对

以下页面于 2026-11-06 直接联网读取，并与当前源码交叉检查：

1. [Electron Performance](https://www.electronjs.org/docs/latest/tutorial/performance)：推迟非首屏工作；避免 Main 长任务与同步 I/O；耗时渲染工作使用 Worker。支持首屏拆分与主进程报告处理的调查方向。
2. [Electron WebPreferences](https://www.electronjs.org/docs/latest/api/structures/web-preferences)：`backgroundThrottling` 默认开启；禁用对可见性与同窗口换帧的影响，说明应按网页用途设计策略。
3. [React lazy](https://react.dev/reference/react/lazy)：首次渲染时才加载模块；在组件外声明，避免意外重置状态。项目现有 `lazyPanel` / `LoadWhenVisible` 可直接承接。
4. [MDN Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)：隐藏页 RAF 与定时器会受浏览器调度；需要按 visibility 明确暂停读取，而非只等待定时器被节流。
5. [Node.js Don't Block the Event Loop](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)：大 JSON 的 parse/stringify 和长计算仍会占用事件循环；异步文件 API 本身不能消除这些 CPU 成本，可考虑分片或移到 Worker。
6. [Chrome Fix memory problems](https://developer.chrome.com/docs/devtools/memory-problems)：区分泄漏、内存膨胀与频繁 GC；结合进程趋势、heap snapshot、detached DOM 和 allocation timeline 定位，不能仅凭 RSS 未下降判泄漏。
