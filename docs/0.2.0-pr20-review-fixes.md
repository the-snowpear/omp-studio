## 2. 根因证据（文件 / 函数 / 复现方法）

### P1-1 封包上限不一致

- `apps/desktop/src/ipc.ts:134`（等价于 `:254` 的切片循环）`const MAX_IDS_PER_EVENT = 64;`
- `apps/desktop/src/ipc-validation.ts:65` `const MAX_EVENT_IDS = 32;`，用于 `isSubscriptionEventEnvelope()` 的 `ids.length > MAX_EVENT_IDS` 判定
- preload 的 `onEvent`（`ipc-validation.ts` 内）对非法封包直接 `return` —— **逐监听器静默丢弃**

触发条件：同一 scope 有 33–64 个订阅 id。产品里 `{ scope: "all" }` 被多处订阅（`App.tsx`、`GitStatusPanel`、`useGitRepository`、`ModelDelegationList`、`runtimeUpgrade`、`conversationSource`），叠加后即可超过 32。
影响：这些合法订阅者收不到任何事件，且没有任何错误或日志。
复现：在旧实现上跑新测试（Main 的 fake `sender.send` → 真实 `createDesktopIpcBridge`）：

```

  AssertionError: every subscriber must get the event exactly once
  + [ { hits: 0, index: 0 }, { hits: 0, index: 1 }, … ]   // 33 个订阅者全部 0 次
✖ 64 … ✖ 65 … ✖ 128 …            tests 27  pass 23  fail 4
```

### P1-2 执行边界的信任缺口

- `packages/studio-host/src/runtime-resolver.ts`（改动前 `:319` / `:359`）：探针前 `fingerprint(..., { fresh: true })`，探针后普通 `fingerprint()`，后者命中 `ExecutableFingerprintCache` —— 复用规则是"`lstat` 的 size/mtimeMs/inode/dev 未变即复用"。
- `packages/runtime-installer/src/installer.ts` 的 `currentManifest()` 用同一套 stat 键证据缓存（TTL 10 分钟）验证 entrypoint 字节。

两个具体缺口：

1. **探针前后**：同长度原地覆写 + 还原 `mtime`，`lstat` 全部相同 ⇒ 探针后的"重新校验"直接返回探针前的指纹，`IDENTITY_MISMATCH` 永不触发。
2. **签名覆盖**：identity 是 `sha256(platform\0 || bytes)`，`checksums.json` 是 `sha256(bytes)`；两者不同源，且执行边界**从未**把"当前字节"与"签名覆盖的摘要"比对过。于是"重新算出指纹"只证明"自读过以来没变"，不证明"这是被签名的那份产物"。

复现：见 §4 的 `an in-place rewrite with a restored mtime is still detected after the probe` 与 `a managed Runtime whose bytes do not match the signed checksum never reaches the probe`（旧实现在两条上都放行）。

### P1-3 降级写覆盖其他会话

- `apps/renderer/src/dock/store.ts`（改动前 `:213-216` / `:238`）：`payload(slim=true)` 只保留当前 scope 的布局、`recent` 清空，却仍写 `STORAGE_KEY = "omp.dock.v1"`。
- 配额不足 ⇒ 全量写抛错 ⇒ 精简写**因为更小反而成功** ⇒ 其他会话的布局被永久替换。

复现：把 `payload()` 临时还原为旧实现，跑主回归用例：

```
× a degraded write keeps every other session's layout, preset and default
  - "panels": [ "problems", "tests", "output", "logs", "pvlogs" ]        ← 会话 A 本应含 terminal
  + "panels": [ "terminal", "problems", "tests", "output", "logs", "pvlogs" ]
  "files": { - "collapsed": false, - "height": null  + "collapsed": true, + "height": 320 }
```

### P2-1 未挂载终端的"假 ACK"

- `apps/renderer/src/terminalSessions.tsx`（改动前 `:117` / `:118`）：
  ```ts
  this.pending.set(event.id, ((this.pending.get(event.id) ?? "") + decoded.text).slice(-PENDING_MAX_CHARS)); // 只留 64K 字符
  ```

## 3. 修复实现（关键设计选择与理由）

### P1-1：协议常量单点 + 分片不变

```ts
// packages/transport-desktop/src/channels.ts
export const DESKTOP_IPC_LIMITS = Object.freeze({ maxSubscriptionIdsPerEvent: 64 });
// apps/desktop/src/ipc.ts            const MAX_IDS_PER_EVENT = DESKTOP_IPC_LIMITS.maxSubscriptionIdsPerEvent;
// apps/desktop/src/ipc-validation.ts const MAX_EVENT_IDS   = DESKTOP_IPC_LIMITS.maxSubscriptionIdsPerEvent;
```

- 选择**协议包**作为常量的家：它已经是通道名的唯一来源，Main 与 preload 都依赖它（preload 由 esbuild 内联，无运行时耦合）。
- 取 64（而不是把 Main 降到 32）：Main 原有的分片尺寸与消息数保持不变，改动只发生在 preload 的解析上限；代价是需要 Main/preload 同版本发布（见 §7）。
- 分片逻辑未改：超过 N 个 id 切成多条封包，每个 id 恰好出现在一条里；同一 scope 仍只开**一个** Host 订阅（测试断言 `subscribeCalls()===1`），没有退回"每个订阅一个 Host 订阅"。

### P1-2：执行边界重读 + 单趟双摘要 + 签名摘要比对

信任链现在是：

```
签名的 runtime-manifest.json / checksums.json
      │  ← currentManifest()：每次都全量验签（metadata + ed25519），非执行查询可用证据缓存
      ▼
签名覆盖的 entrypoint 摘要（installer 现在把它作为 entrypointSha256 一并返回）
      │
      ▼
readExecutableDigests()：一次流式读，同时算
   • identity   = sha256("${platform}\0" || bytes)   ← 冻结算法，Thread binding 依赖
   • contentSha256 = sha256(bytes)                    ← 与 checksums.json 同源
      │
      ├─ 探针前：managed 要求 contentSha256 === 签名摘要，否则拒绝（探针不执行）
      ▼
   probe（真正执行该文件）
      │
      ├─ 探针后：再读一次，要求 identity 与 contentSha256 都和探针前一致
      ▼
   spawn
```

- **为什么必须读两次**：探针执行了文件，之后必须证明"磁盘上的字节仍是探针前批准的那份"。只比 `lstat` 无法证明（同长度原地覆写 + 还原 mtime 可以绕过）；`ExecutableFingerprintCache` 正是把"复用"放在了这个位置，因此**删除该类**（而不是留着不用，避免后人再启用）。`host-backend` 的共享指纹缓存与 `invalidateRuntimeVerification()` 的对应部分一并移除。
- **为什么单趟双摘要**：一次读同时产出 identity 与 content，执行边界不因为"既要绑定身份又要对签名"而读两遍文件。
- **谁负责什么**：installer 的证据缓存继续服务非执行查询（版本、状态、`usage.get`），它是**唯一**还会只看元数据的地方，且有 10 分钟上限与显式 `invalidate()`；`resolveRuntime` 不再信任任何缓存。managed 查询若拿不到签名摘要 ⇒ **fail closed**。
- **TOCTOU 剩余风险**：探针后读取到 `spawn` 之间仍存在窗口，攻击者需要对 Runtime 目录有写权限；关闭它需要"持有 fd 再 spawn"，三个后端（node-pty / pipes / SSH）不可移植。已在 §6 如实说明，不声称绝对安全。

### P1-3：三级写入 + 只丢派生缓存

```
1. 全量：全部 sessions + recent + presets + preferences
2. 失败 → 去掉 recent（派生缓存，下次成功保存即重建），sessions/presets/preferences 全保留
   并在降级前把上一次成功的原始载荷写进 omp.dock.v1.backup（仅当该键不存在时写一次）
3. 仍失败 → 不写：上次成功载荷原样保留，本实例 blocked = true 停止自动重试
```

- 没有改成"按会话分 key"：本轮优先最小改动，避免迁移 + 回滚的新风险；现有 key 格式、`version:1`、`migrated`、旧 `omp.layoutMemory.*` 迁移、预览隔离、草稿 scope 语义全部不变。
- 200 ms 合批与四个边界 flush（scope 切换 / draft 交接 / `pagehide` / `beforeunload` / `visibilitychange→hidden`）保留，测试断言 20 次 dispatch 只产生 1 次写。

### P2-1：ACK = 已写入；有界队列 + 显式溢出

| 场景 | 行为 |
|---|---|
| 有 xterm host | `term.write(text, cb)`，cb 里才 ACK（同 tick 合并成一条 IPC） |
| 无 host | 入队（**按 `event.bytes` 计量**、FIFO），**零 ACK** ⇒ Main `unacked` 增长 ⇒ 500 KiB 处 pause PTY |
| 队列达 3 MiB（异常：源没被真正暂停） | 丢**最旧**、保最新；写一条 sticky notice；保留尾巴写入后才补一次丢弃字节的 ACK（否则 PTY 永远回不到 LOW 水位） |
| 纯图形 / 零文本批次 | 立即 ACK（不占队列，且不会让 Main 停在暂停） |
| exit / close / dispose | 会话封口（`#sealed`）：迟到回调不再 ACK；队列尽力写入后释放，不泄漏 |

- 上界依据：Main 在 500 KiB 未确认时暂停，但其自身硬上限 2 MiB 仍可能先交付 ⇒ 最坏 2.5 MiB 会到达渲染侧，故队列取 **3 MiB**；正常路径永远触不到上限。
- 内存上界：3 MiB/终端 × 最多 8 终端 = 最坏 24 MiB，且仅在"未挂载 + 源未被暂停"的异常窗口里。
- **Main 生产代码零改动**：`pause()` 已覆盖本地 node-pty、pipes 后端与 SSH；`acknowledge()` 对 ACK 做裁剪；`close()` 会 `decoder.end()` 刷尾。本轮只补了 SSH 侧的一致性测试。

## 6. 安全性说明：Runtime 签名与指纹校验的最终信任边界

| 问题 | 现在由什么回答 | 说明 |
|---|---|---|
| 这份安装是否由可信密钥签名？ | `verifySignedMetadata()`，**每次** `currentManifest()` 都执行（manifest + checksums + payloadSha256 + ed25519） | 未削弱 |
| 要执行的字节是否就是被签名的那份？ | **执行边界**：`readExecutableDigests()` 的 `contentSha256` vs 签名覆盖的 `checksums.json` 摘要 | 新增；此前没有这一层 |
| 探针执行前后文件是否变化？ | 探针前/后各一次完整读，比较 identity 与 contentSha256 | 从"stat 比较"改为"内容比较" |
| 这个 identity 是否可信（用于 Thread binding）？ | 冻结算法 `sha256(platform\0‖bytes)`，边界当场计算 | 算法未变，兼容既有 binding |
| 非执行查询（版本/状态/`usage.get`）是否安全？ | installer 证据缓存：stat 身份 + 断言 + 10 分钟 TTL + 进程启动即空 + install/activate/rollback/uninstall/prune 全失效 + `invalidate()` 作废在途读 | 它是**唯一**还按元数据信任的地方，且不参与执行准入 |
| 失败时？ | 签名失败 / 摘要不符 / 无签名摘要 / 读失败 ⇒ 一律拒绝，探针不执行 | fail closed |

**剩余风险（明确不声称绝对安全）**：

1. **TOCTOU**：探针后的读取与 `spawn` 之间仍有一个窗口；攻击者需要能写 Runtime 目录（通常已等价于本机同用户权限）。关闭它需要"持有文件描述符再 spawn"，而 node-pty / pipes / SSH 三个后端不可移植。
2. **非执行路径的 10 分钟信任窗口**：在同一 stat 指纹下替换文件且不触发任何边界，最多 10 分钟内状态/用量显示可能来自旧证据；但**执行**不受此影响（每次 spawn 都重读并与签名比对）。
3. **签名密钥本身**：仍依赖打包时注入的 trusted public key 与 `checksums.json` 的覆盖要求（未改）。

## 10. 复审补修（第四轮）：终端自然退出丢失未挂载输出

复审 HEAD `7377c65`。本轮只处理这一项生命周期回归，没有重做性能测试，也没有改动 §1–§9 的结论。

### 10.1 红色测试证据（先复现，再修）

在旧实现上新增 11 个用例，其中 **8 个失败**（`vitest run src/terminalSessions.test.tsx`，旧实现 `Tests 8 failed | 27 passed (35)`）：

```
× a natural exit keeps an unmounted terminal's output for the first attach
× a chunk that arrives after the exit event is appended, not dropped
× replays the whole backlog on the first attach after the exit
× keeps output from both sides of the exit in arrival order
× re-attaching an ended terminal does not replay the output twice
× keeps truncation visible after a natural exit and clears it on close
× releases an ended terminal when the user closes it
× drops nothing when the process exits before create returns
```

最直接的一条：未挂载时收到 `queued-but-never-shown`，进程自然退出后
`store.pending.get(id)` 变成 `undefined` —— 用户之后打开这个终端只会看到空白。

被替换的错误断言（旧测试把"丢数据"写成了期望）：

```
- it("an exit while unmounted clears the queue and sends no ACK")   → expect(pending).toBeUndefined()
+ it("a natural exit keeps an unmounted terminal's output for the first attach")
+   expect(store.pending.get(id)?.text).toBe("queued-but-never-shown")
```

### 10.2 代码根因

`apps/renderer/src/terminalSessions.tsx`（修复前）：

1. `onExit` → `#sealed.add(id)` + `#flushBestEffort(id)`；后者**无论有没有 host 都** `queue.clear()` + `pending.delete(id)`
   ⇒ 未挂载终端的全部待显示输出在进程结束瞬间被丢弃。
2. `onData` 的守卫 `if (this.#sealed.has(event.id) && this.hosts.get(event.id) === undefined) return;`
   ⇒ 退出后合法到达的尾部输出（Main 侧真实存在，见 §10.5）被直接丢进黑洞。
3. `#sealed` 同时承担三件事：不 ACK、丢弃尾部数据、资源已释放。三种语义混在一个集合里，
   所以"进程结束"被当成了"用户关掉终端"。

### 10.3 修改的生命周期规则

把原来的一维 `#sealed` 拆成两个正交状态：

| 状态 | 触发 | 语义 |
|---|---|---|
| **running** | `create()` 返回且进程未退出 | 有 host：写 xterm 后 ACK；无 host：入有界队列、**不 ACK**（Main 500 KiB 水位背压） |
| **ended**（新：`#creditsClosed`） | `onExit`（自然退出或 kill） | **仍接收**尾部输出、仍可显示/排队；**永不 ACK**；不再发放新的流控额度 |
| **released**（新：`#released`） | `remove()`（用户关标签）/ `close()`（窗口销毁） | 释放 screen、队列、decoder、notice；此后**忽略任何迟到事件**，不重建队列 |

关键改动：

- `onExit`：`#creditsClosed.add(id)` + 丢弃该 id 的待发 ACK + `#deliverEnded(id)`。
  `#deliverEnded` **只在已挂载 screen 时**把队列写进 xterm 并释放队列；**没有 screen 就原样保留**。
- `attachHost`：`#creditsClosed` 的终端走"只显示不记账"的回放（写一次并清空队列，不给写入回调 ⇒ 不会 ACK），
  运行中的终端仍走原来的 `#drain`（每批写入后 ACK）。
- `onData`：`#released` 直接 return；`ended` 终端继续接收 —— 有 host 就直接写（不带回调），无 host 就入同一个
  3 MiB 有界队列；两条路径都不 ACK。
- `#ack` / `#flushAcks`：`#creditsClosed` 与 `#released` 都不再发送 ACK。
- `#releaseScreen`：标记 `#released` 并清理 screen/队列/decoder/ACK/**notice**。
- `#queue` 的创建路径受 `#released` 守卫，用户关闭后不会因尾部事件重新长出队列。

缓冲、顺序与提示语义保持上一轮：`PENDING_MAX_BYTES = 3 * 1024 * 1024` 不变、按到达顺序、丢最旧、
截断提示 sticky（自然退出后仍可见，直到用户关闭该终端）；图形/零文本批次仍立即 ACK（它们不占队列）。

### 10.5 Main/Renderer 退出顺序：**不需要协议变更**

核对 `apps/desktop/src/terminal-pty.ts` 的既有契约（未改动）：

- **自然退出**（`proc.onExit`）：`#batcher.flush(id)` → `#markEnded` → `listeners.onExit({ id })` →
  `setTimeout(TERMINAL_BATCH_MS /* 8ms */)` 后 `#batcher.close(id)`。
  ⇒ 退出通知之后**最多一个合批窗口**内仍可能有尾部 `onData`；这正是 Renderer 必须接收的合法尾部输出。
- **用户 kill/关闭**（`#kill`）：`#batcher.close(id)`（把尾巴投递出去）**先于** `onExit` ⇒ 该路径没有退出后数据。
- `terminal-batch` 的常量（8 ms / 2 MiB / 500 KiB / 100 KiB）与 `acknowledge()` 的裁剪逻辑本轮**零改动**
  （`git diff` 为空）。

所以只需 Renderer 侧放宽"退出即拒收"，不需要新 IPC、不需要定时器、不需要改动 Main。

### 10.6 是否仍存在尾部输出丢失风险

- **已消除**：自然退出不再丢弃待显示队列；退出后的合法尾部数据不再被丢弃；已结束终端不发放 ACK；
  用户关闭后不会因迟到事件重建队列或泄漏内存。
- **保留的显式取舍**：单终端队列仍有 3 MiB 上限，超过时丢**最旧**并显示 sticky notice（不是静默丢失）；
  未挂载且用户一直不打开的已结束终端会保留 ≤3 MiB 直到关闭（有界，不再增长）。
- **未验证**：真实 ConPTY 洪水 + 折叠/展开的真机手感、真实 SSH 会话的自然退出（本轮的真实 Electron 验证只覆盖
